# Phase 1.3 Mutation Contracts

Status: **Phase 1.3.0 contract frozen**

Contract draft: 2026-08-31

Remediation review: 2026-09-01

Phase 1.3.2.0 amendment status: **Approved — pending merge/seal**

This document is the authoritative public contract for the Phase 1.3 draft mutation abilities. Phase 1.3.1 implemented and validated the two Create Draft abilities; the dedicated Direct MCP server now exposes exactly ten tools (the eight Phase 1.2 read-only tools plus the two Create Draft tools). The base Update contracts remain frozen but unimplemented; the narrow Phase 1.3.2.0 sentinel amendment below is approved pending merge/seal.

## Contract goals

Phase 1.3 adds narrowly scoped draft creation and draft editing without granting an MCP client a generic WordPress write surface. The eventual implementation must preserve the existing architecture:

```text
MCP client
-> official WordPress MCP Adapter
-> WordPress Abilities API
-> WP-Auto mutation ability
-> shared WP-Auto mutation service
-> WordPress Core APIs
```

Direct MCP and a future explicitly enabled Cloud MCP integration must call the same WP-Auto abilities. MCP transport authentication is not a substitute for the capability and object checks defined here.

## Shared mutation rules

- Every input and output schema is a strict object with `additionalProperties: false`.
- Post abilities always operate on the built-in `post` post type. Page abilities always operate on the built-in `page` post type.
- All created objects are drafts owned by the current authenticated WordPress user.
- Update abilities may edit an existing draft only; they never change its type, status, author, parent, dates, password, taxonomy, template, menu order, comment settings, ping settings, media, or metadata.
- The implementation must pass only allowlisted fields to WordPress Core.
- Capability checks are repeated in the service immediately before privileged work.
- Returned values describe the final object re-read from WordPress after Core filters, sanitization, KSES, slug canonicalization, and hooks have run.
- `edit_url` is generated by WordPress Core and never contains a nonce.
- User-facing errors are translatable and never expose Core errors, SQL, filesystem paths, stack traces, metadata, credentials, or request bodies.

String length limits use the WordPress schema validation path. The service still enforces semantic rules that JSON Schema cannot express, including rejecting a title that contains only whitespace.

## Create Draft contracts

The Post and Page Create Draft abilities share the same schema and differ only in their fixed post type, capability object, and output `type` value.

### Input schema

Required fields:

| Field | Type | Contract |
| --- | --- | --- |
| `title` | string | 1–500 characters; after validation it must contain at least one non-whitespace character |
| `idempotency_key` | string | 8–128 characters; pattern `^[A-Za-z0-9][A-Za-z0-9._:-]{7,127}$` |

Optional fields:

| Field | Type | Contract |
| --- | --- | --- |
| `content` | string | maximum 1,000,000 characters |
| `excerpt` | string | maximum 50,000 characters |
| `slug` | string | 1–200 characters when supplied |

Optional fields omitted by the caller are normalized to an empty string for the idempotency fingerprint. This normalization does not let the client set any field outside the contract.

The client cannot provide or override `post_type`, `post_status`, `post_author`, dates, password, taxonomy, terms, featured media, metadata, template, parent, menu order, comments, pings, revisions, GUID, or arbitrary Core arguments.

### Server-fixed values

| Ability | `post_type` | `post_status` | `post_author` | Page parent |
| --- | --- | --- | --- | --- |
| `wp-auto/post-create-draft` | `post` | `draft` | current authenticated user ID | not applicable |
| `wp-auto/page-create-draft` | `page` | `draft` | current authenticated user ID | `0` |

### Authorization

The Ability `permission_callback` and the mutation service both obtain the fixed post type object and require its actual `cap->create_posts` capability. The contract does not hard-code `edit_posts` or `edit_pages`, even though those are the current built-in mappings. Role names, `manage_options`, and administrator checks are prohibited.

### Output schema

Every field is required and no additional field is returned:

| Field | Type | Contract |
| --- | --- | --- |
| `id` | integer | created or replayed object ID |
| `type` | string | fixed enum `post` or `page` for the Ability |
| `status` | string | fixed enum `draft` |
| `slug` | string | final Core-stored slug |
| `link` | string | final Core-generated permalink |
| `edit_url` | string | Core-generated edit URL without a nonce |
| `modified_gmt` | string | final raw Core `post_modified_gmt`; may be `0000-00-00 00:00:00` or a normal GMT datetime |
| `idempotency_replayed` | boolean | `false` for the creating execution; `true` for a safe completed replay |

Ability annotations:

```text
idempotent=true
```

## Create idempotency state machine

The Phase 1.3 model is **concurrent-safe persistent idempotency with deterministic replay for completed operations**. Atomic claim acquisition prevents two live requests from owning the same scope at once; it is not an unconditional guarantee of exactly-once object creation across every possible Core hook, database failure, or process crash.

Idempotency scope is:

```text
site + actor user ID + Ability name + idempotency_key
```

The future implementation must derive a scope hash and store the private, non-autoloaded site option `wp_auto_connector_idempotency_<scope-hash>`. It must use the uniqueness of `add_option()` as the atomic claim. A transient, process-local lock, or post meta alone is insufficient.

The option never stores the raw idempotency key, content fields, or complete request. Its fixed record contains only:

```text
version
actor user ID
Ability name
SHA-256 payload fingerprint
state
target object ID, when known
created/updated GMT timestamps
```

The canonical payload fingerprint hashes fields in the exact order `title`, `content`, `excerpt`, `slug`. An omitted optional field is represented as an empty string. The key, timestamps, IDs, permalink, status, and derived values are excluded.

The state machine has these logical states. Their exact stored labels and representation are implementation details:

| Logical state | Meaning and permitted transition |
| --- | --- |
| claimed / in-progress | One request owns the atomic claim or an earlier operation has not been resolved. No other request may create. |
| completed | A target and matching fingerprint were finalized and may be replayed after verification. |
| conflict | The same scope/key was presented with a different fingerprint or a completed result cannot be replayed safely. No create is attempted. |
| recoverable-stale-or-failed | Deterministic recovery has proved that Core created no object, so the implementation may safely resume or reacquire according to one documented implementation path. |

Required behavior:

1. **New scope/key:** atomically acquire the persistent claim, then perform one Core Create attempt. A successfully finalized create returns `idempotency_replayed=false`.
2. **Completed same request:** the actor, Ability, key scope, and fingerprint must match. After verifying that the original target still exists, has the correct type and draft status, and is editable by the actor, return that original operation's target as the completed result with `idempotency_replayed=true`. The response is reconstructed from the verified current Core object; no new draft and no new audit event are created.
3. **Same key, different payload:** do not create. Return `wp_auto_idempotency_conflict` with semantic status 409.
4. **Live in-progress operation:** do not create. Deterministically return `wp_auto_idempotency_in_progress` with semantic status 409.
5. **Stale, failed, or interrupted claim:** never permit an immediate new Create. A deterministic resolver must first establish one of three outcomes: recover and complete/replay a verified target; prove that Core created no object and move through the recoverable state before retrying; or retain the blocking claim when the outcome is uncertain. An uncertain claim must not be expired merely because time passed.
6. **Write/finalization uncertainty:** if `wp_insert_post()` may have succeeded but target correlation, invariant verification, claim completion, or audit finalization fails, keep authoritative idempotency state and return `wp_auto_mutation_state_uncertain`. A later request cannot create again until deterministic resolution proves that doing so cannot duplicate the original operation.

A claim may be released or made retryable only when the implementation can prove that Core created no object. The exact Phase 1.3.1 correlation and recovery mechanism remains an implementation detail, but it must satisfy the non-duplicating outcomes above and be covered by crash-point tests before exposure.

The authoritative idempotency record is persistent local WordPress state and must survive HTTP retries, PHP process restarts, and ordinary request failure. Request memory, static PHP variables, process-local caches, transients alone, and the bounded audit history are not authoritative idempotency state.

## Update Draft contracts

The Post and Page Update abilities share the same schema and differ only in their required object type and capability object.

### Input schema

Required fields:

| Field | Type | Contract |
| --- | --- | --- |
| `id` | integer | minimum 1 |
| `expected_modified_gmt` | string | exactly 19 characters matching `^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}$`; semantic validation accepts either the exact Core sentinel `0000-00-00 00:00:00` or a real GMT calendar datetime |

Optional mutable fields:

| Field | Type | Contract |
| --- | --- | --- |
| `title` | string | 0–500 characters |
| `content` | string | maximum 1,000,000 characters |
| `excerpt` | string | maximum 50,000 characters |
| `slug` | string | 1–200 characters when supplied |

At least one mutable field must be present. Omitted fields remain unchanged. `title`, `content`, and `excerpt` may be explicitly emptied, but after merging the supplied changes with the stored object the service rejects a field combination that Core cannot accept as meaningful content. A supplied `slug` can never be empty.

### Authorization, status, and existence hiding

The Ability baseline obtains the fixed post type object and requires its actual `cap->edit_posts` capability. The service then requires `current_user_can( 'edit_post', $id )` for the target.

Missing objects, wrong post types, and unauthorized objects all return `wp_auto_content_not_found` with semantic status 404. Only after the object type and object-level permission have passed may the service disclose that an object is not a draft; an authorized non-draft returns `wp_auto_content_status_conflict` with status 409. WordPress Core remains free to map additional object-specific requirements, including privacy policy capabilities.

### Best-effort optimistic stale-write detection

The service executes these steps in order:

1. validate the complete strict input;
2. fetch the required object type;
3. perform object-level `edit_post` authorization;
4. require current status `draft`;
5. immediately before invoking the WordPress Core update path, re-fetch the latest Core object and compare `post_modified_gmt` exactly with `expected_modified_gmt`;
6. install the operation-scoped invariant guard;
7. call the Core update API with allowlisted fields only;
8. remove the guard in `finally`, re-fetch, and verify the result;
9. append the bounded local audit event.

Phase 1.3 uses `expected_modified_gmt` as a best-effort optimistic concurrency precondition. If it already differs from the current WordPress `post_modified_gmt` at the final comparison, no WP-Auto update is attempted, `wp_auto_content_conflict` is returned with semantic status 409, and current content is not returned. The client must call the matching Get ability before retrying.

### Phase 1.3.2.0 `modified_gmt` sentinel compatibility amendment

Status: **Approved — pending merge/seal**. This is a documentation-only amendment; no Update Ability or MCP tool is currently registered, and the planned JSON Schema remains unchanged.

The exact WordPress Core sentinel `0000-00-00 00:00:00` is a valid opaque concurrency token when returned by Core for a draft. It is the only zero-date exception. Every other value must remain a real GMT calendar datetime in the existing `YYYY-MM-DD HH:MM:SS` shape. The sentinel is not interpreted as a date and is not a stronger version token.

The service must compare the client's token and the latest raw Core `post_modified_gmt` as exact strings. It must not normalize, parse-and-reformat, convert, shim, or synthesize either value. A sentinel/current-sentinel pair matches; a sentinel/current-real or real/current-sentinel pair conflicts; equal real timestamps match; different real timestamps conflict. A mismatch continues to use `wp_auto_content_conflict` with semantic status 409. Malformed or impossible non-sentinel input continues to use `wp_auto_invalid_request` with semantic status 400. No new error code is introduced.

Mutation outputs continue to return the final raw Core `post_modified_gmt`, so `modified_gmt` may contain the exact sentinel or a normal GMT datetime. The second-level precision, same-second ambiguity, and check-to-write race remain unchanged; this amendment does not provide CAS, transactions, locks, revisions, ETags, or stronger lost-update prevention.

This final comparison is not an atomic compare-and-swap guarantee. A concurrent browser, background process, plugin, or other external writer can update the object after WP-Auto compares the timestamp but before WordPress completes the update. Phase 1.3 therefore does not guarantee prevention of every lost-update race under arbitrary concurrent external writers and never claims that stale writes are always prevented.

WordPress `post_modified_gmt` is the Phase 1.3 MVP concurrency token and has second-level timestamp granularity. Multiple updates within the same second may not be distinguishable by `modified_gmt` alone. A stronger revision, version, or atomic CAS model would require an explicit future contract revision and is outside Phase 1.3. Phase 1.2 Get output is not changed to add an ETag, revision, or version field.

Phase 1.3 intentionally stays on the WordPress Core mutation path. It does not require a direct `$wpdb` conditional `UPDATE`, `SELECT ... FOR UPDATE`, or custom transaction locking solely to simulate atomic CAS, because doing so would bypass or distort Core hooks, revisions, sanitization, cache invalidation, capability handling, and plugin interoperability.

## Invariant guard and post-write verification

The future shared mutation service must install a narrowly scoped final data guard only for the current operation and must remove it in `finally`. Immediately before Core persists the object, the guard reasserts the fixed type, draft status, and author. It also prevents an update from changing Page parent or any other non-contract field. The service then re-reads the object and verifies those invariants after Core returns.

The guard is defense in depth against filters and accidental field flow. It is not permission to bypass legitimate Core capability, KSES, validation, or sanitization behavior.

## Local mutation audit

Each content object stores a private `_wp_auto_connector_mutation_audit` metadata value containing up to the 20 most recent WP-Auto mutation attribution events for that object. This is a per-object limit, not a site-wide 20-event history. When appending event 21 for that object, the oldest event for the same object is removed.

Every event contains only:

```text
version
operation
Ability name
actor user ID
target object ID
timestamp_gmt
```

Create events additionally contain the SHA-256 fingerprint, never the raw idempotency key. Update events additionally contain expected and resulting `modified_gmt`. Events never contain title, content, excerpt, slug, request bodies, credentials, or external identifiers.

The bounded audit history is human-readable attribution and is **not authoritative idempotency state**. Pruning an old audit entry may discard attribution history, but it must never delete, expire, or weaken an active or completed idempotency guarantee. Audit and idempotency may later share implementation infrastructure, but their lifecycle and retention semantics remain separate; the last 20 audit entries can never be the only source used to determine whether a key completed.

The audit metadata is not returned by Phase 1.2 tools, is never client-writable, and never leaves WordPress through a WP-Auto external request. A successful idempotency replay does not append an event. If content may have been written but the audit cannot be finalized, the service returns `wp_auto_mutation_state_uncertain`; it does not claim the content write was rolled back.

## Mutation and side-effect boundary

Phase 1.3 distinguishes three categories:

### A. Requested domain mutation

- create the requested Post or Page draft with server-fixed invariants; or
- update only the requested, allowlisted fields on the authorized target draft.

### B. Expected WordPress Core or plugin lifecycle side effects

- Core may associate the site's default category when creating a Post;
- an Update may create a WordPress revision;
- Core updates `post_modified` and `post_modified_gmt`;
- Core performs cache invalidation;
- WordPress and plugin hooks may run;
- KSES, `unfiltered_html`, slashing, sanitization, and canonical slug generation remain effective;
- Core or plugins may maintain internal metadata as part of their normal lifecycle.

These effects are not automatically WP-Auto contract violations. Mutation output and later Get results represent final stored state and do not promise byte-for-byte preservation of submitted HTML. They also do not grant the MCP client direct control over default taxonomy, revisions, internal metadata, hooks, or caches.

### C. Forbidden WP-Auto side effects

WP-Auto must not intentionally publish or promote status, mutate an unrelated Post/Page, assign or change taxonomy, upload or change media, change a featured image, change SEO metadata, write arbitrary metadata, mutate users/settings/plugins/themes, or perform external Cloud/telemetry mutation. The expected Core default-category association does not authorize WP-Auto to issue its own taxonomy mutation.

## Error contract

| Code | Semantic status | Meaning |
| --- | ---: | --- |
| `wp_auto_invalid_request` | 400 | invalid type, bound, date, field combination, or unknown input |
| `wp_auto_content_not_found` | 404 | Update target is missing, wrong type, or unauthorized |
| `wp_auto_idempotency_conflict` | 409 | key payload conflict or completed record cannot be replayed safely |
| `wp_auto_idempotency_in_progress` | 409 | identical scope has a concurrent or unresolved claim |
| `wp_auto_content_status_conflict` | 409 | authorized Update target is not a draft |
| `wp_auto_content_conflict` | 409 | `expected_modified_gmt` does not match the latest object |
| `wp_auto_content_create_failed` | 500 | Core Create failure with proof that no object was created |
| `wp_auto_content_update_failed` | 500 | Core Update failure with proof that the requested write was not applied |
| `wp_auto_mutation_state_uncertain` | 500 | Core may have written, but result or internal state cannot be confirmed |

Ability capability denial continues to be handled by the WordPress Abilities/MCP Adapter layer. Adapter schema errors, transport HTTP 401/403, WP-Auto semantic status, and MCP `isError` are separate protocol layers.
